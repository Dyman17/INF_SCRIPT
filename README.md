# Classroom Control System (Учитель/Ученик + AI-анализ)

## 0. Общее описание проекта

Проект представляет собой школьную систему контроля учебных ПК с единым клиентским приложением на WinForms, где при входе выбирается роль: `teacher` или `student`.

- роль `teacher` получает панель мониторинга, управление режимом урока и просмотр предупреждений;
- роль `student` запускает агент, который в фоне собирает телеметрию и применяет политики ограничений.

Инфраструктура проекта:

- **Backend** размещается на Render и отвечает за API, авторизацию, хранение/чтение телеметрии, политики и предупреждения;
- **Database** размещается в Supabase (PostgreSQL + политики доступа);
- **Desktop App (WinForms)** работает на всех ПК, но открывает разный функционал в зависимости от роли пользователя.

Базовый рабочий сценарий:

1. Учитель включает режим урока.
2. Ученические клиенты периодически отправляют JSON со списком процессов.
3. Сервер сохраняет данные в Supabase, анализирует активность (в том числе через AI API) и формирует предупреждения.
4. Учитель видит потенциально неучебные активности и принимает решение вручную.

Первый технический шаг проекта: реализовать надежный сбор процессов на ученическом ПК, сериализацию в JSON и отправку на backend.

---

## 1. Идея проекта

Система для кабинета информатики (например, 16 ученических ПК + 1 ПК учителя), которая:

- централизованно управляет ученическими компьютерами во время урока;
- ограничивает запуск игр и неучебных приложений;
- собирает телеметрию (запущенные процессы, активные окна, вкладки браузера);
- отправляет данные на AI API каждые 5 минут;
- показывает учителю потенциально неуместные активности.

Основная цель: не тотальный запрет всего подряд, а контроль и быстрый сигнал учителю о том, что ученик отвлекся.

---

## 2. Общая архитектура

### 2.1 Компоненты

1. **Cloud Server (центральный сервер)**
   - хранит политики урока;
   - принимает статусы от ученических ПК;
   - отправляет команды агентам;
   - обращается к AI API для анализа активности;
   - отдает данные панели учителя.

2. **Teacher App (WinForms)**
   - интерфейс учителя;
   - кнопки: `Начать урок`, `Режим контроля`, `Снять ограничения`, `Заблокировать экран` (опционально);
   - отображение списка ПК, статусов, предупреждений от AI.

3. **Student Agent (WinForms + Windows Service логика)**
   - установлен на каждом ученическом ПК;
   - работает в фоне;
   - собирает локальную активность (процессы, активные окна, домены/вкладки);
   - применяет правила блокировки;
   - отправляет данные на сервер.

4. **AI API модуль**
   - получает сводку активности ученика за интервал (5 минут);
   - определяет “потенциально неучебные” активности;
   - возвращает метки и уровень риска;
   - эти метки показываются учителю в панели.

> Важно: для надежности агент должен работать как служба Windows. Если сделать только обычный WinForms-процесс, ученик может его закрыть.

---

## 3. Как это работает (рабочий цикл)

1. Учитель открывает WinForms-панель и нажимает `Начать урок`.
2. Teacher App отправляет на сервер команду активации режима урока.
3. Сервер пушит политику на все Student Agent:
   - список запрещенных приложений;
   - ограничения по сайтам/категориям;
   - частота отчетов.
4. Каждый агент:
   - отслеживает запущенные процессы и активное окно;
   - при необходимости закрывает запрещенные приложения;
   - собирает события активности.
5. Каждые 5 минут агент отправляет пакет телеметрии на сервер.
6. Сервер формирует AI-запрос (по каждому ПК или батчем) и получает оценку.
7. Если AI видит признаки игр/развлечений/посторонних активностей:
   - ставится флаг `Potentially Non-Learning Activity`;
   - в Teacher App появляется предупреждение.
8. Учитель смотрит предупреждения и принимает решение вручную (например, замечание или точечная блокировка).
9. В конце урока учитель выключает режим контроля.

## 4. Какие данные отправляются в AI каждые 5 минут

Пример минимального набора:

- `studentPcId`
- `timestampStart`, `timestampEnd`
- список процессов (`processName`, `windowTitle`, `durationSec`)
- активные сайты/домены (`domain`, `title`, `durationSec`)
- локальные события блокировок (`blockedProcess`, `blockedAt`)

### Пример JSON-пакета

```json
{
  "studentPcId": "PC-07",
  "period": {
    "start": "2026-04-10T09:00:00Z",
    "end": "2026-04-10T09:05:00Z"
  },
  "processes": [
    {"name": "chrome.exe", "windowTitle": "YouTube", "durationSec": 180},
    {"name": "code.exe", "windowTitle": "main.cs", "durationSec": 90}
  ],
  "domains": [
    {"domain": "youtube.com", "title": "Gaming video", "durationSec": 170},
    {"domain": "learn.microsoft.com", "title": "C# docs", "durationSec": 80}
  ],
  "blockEvents": [
    {"type": "blocked_process", "value": "steam.exe", "time": "2026-04-10T09:03:22Z"}
  ]
}
```

## 5. Что делает AI

AI не должен автоматически “наказывать”. Его роль: **умная фильтрация и подсказка учителю**.

### AI-результат (пример)

```json
{
  "studentPcId": "PC-07",
  "riskScore": 0.82,
  "labels": ["game_related_content", "entertainment_focus"],
  "potentialIssues": [
    "Частое открытие развлекательного видео-контента",
    "Попытка запуска steam.exe"
  ],
  "confidence": "high"
}
```

### В Teacher App показывается

- ПК ученика;
- риск-оценка;
- короткая причина;
- кнопки действий: `Открыть детали`, `Отправить предупреждение`, `Временная блокировка`.

---

## 6. Логика блокировки

### 6.1 Базовые механизмы

- блокировка по имени процесса (`steam.exe`, `epicgameslauncher.exe`, и т.д.);
- блокировка по хешу/пути (чтобы нельзя было обойти переименованием);
- DNS/Firewall-правила для игровых доменов;
- режимы: `Урок`, `Перемена`, `Свободный доступ`.

### 6.2 Рекомендованный принцип

- AI только помечает “подозрительное”;
- окончательное решение всегда за учителем;
- автожесткие санкции по AI-решению не включать на старте проекта.

---

## 7. Безопасность и защита от обхода

- ученические учетные записи без админ-прав;
- агент запускается как `Windows Service` + автозапуск;
- сервер и агент общаются по HTTPS/WSS (TLS);
- у каждого агента свой токен/ключ устройства;
- все действия логируются (кто, когда, что заблокировано).

## 8. Приватность и правила использования

Перед внедрением нужно официально определить:

- какие данные собираются;
- как долго хранятся;
- кто имеет доступ;
- для каких целей используются;
- кто ответственный администратор.

Рекомендуется:

- хранить минимально необходимый набор данных;
- удалять старые логи автоматически;
- показывать уведомление о мониторинге на ученических ПК (по правилам школы/законам региона).

## 9. MVP (первая рабочая версия)

### Что обязательно сделать в MVP

1. Сервер (API + WebSocket).
2. Агент на ученическом ПК (сбор процессов + блокировка по списку).
3. Панель учителя (онлайн-список ПК + режим урока).
4. Отправка агрегированной активности раз в 5 минут.
5. AI-анализ и вывод “Потенциально неучебная активность”.

### Что можно добавить во 2-й версии

- скриншоты по запросу учителя;
- трансляция экрана ученика;
- интеграция с расписанием уроков;
- автоотчеты по классам за неделю.

---

## 10. Технологический стек (предложение)

- **Backend:** ASP.NET Core Web API + SignalR
- **Teacher UI:** WinForms
- **Student Agent:** .NET Worker Service (можно с отдельной WinForms-оболочкой для статуса)
- **Database:** PostgreSQL / SQL Server
- **AI Integration:** OpenAI API (классификация активности по правилам промпта)

---

## 11. Коротко: почему твоя идея хорошая

- централизованный контроль с одного окна учителя;
- AI снижает ручную нагрузку (помогает найти отвлечения);
- можно развивать поэтапно: сначала блокировки, потом “умный” анализ;
- подходит для школьной локальной сети и масштабируется на несколько кабинетов.
